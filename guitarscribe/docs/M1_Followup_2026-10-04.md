# M1 前段診斷與後段回歸（Issue #2）

## 使用者證據

M1 約 55% 正確，第 7 秒後大致正確；M2 約 18%，集中前面幾秒。這些是使用者主觀估計，不是逐音標註準確率。優先 M1，M2 不繼續調整。[Issue #2](https://github.com/jonaschen/guitar_music/issues/2) 保持開啟。

M1 的 220–227 秒約 55.4% 影格有聲、227–233 秒約 67.2% 有聲；前段有聲音高第 10／50／90 百分位約 MIDI 65／72／76.65，後段約 79／86.10／88.73。這些統計不能判定前段真實音高應升八度，亦不能把留白都當作漏音。

## 固定基準，僅兩個單因素檢查

新增 `app.evaluation.melodia_followup`；使用同一 hash 的伴奏、218–235 秒上下文與原始 M1。先重跑 control，若逐影格不等於保存基準就停止，不解讀參數差異。

- R：只把 voicingTolerance 由預設 0.2 改為 0.5，檢查有聲門檻是否漏掉較弱旋律。
- W：只把 maxFrequency 1760 改為 3520Hz，檢查搜尋上限是否排除高音候選。
- 其餘固定；guessUnvoiced 仍 false、不做調性修正／移八度／G 分音、不拼接新舊片段。

選擇這兩個參數是有限診斷假設，不是已確認原因。[官方說明](https://essentia.upf.edu/reference/std_PredominantPitchMelodia.html) 建議大部分參數保持預設，音域與 voicingTolerance 按情境評估。本輪不掃描大量參數，也不新增曲目特例。

## 回歸與重現

前 7 秒及後 6 秒分開計數：新增有聲影格、刪除有聲影格、共有有聲影格中超過半音的變更。任何計數皆不等於音樂正確率；待使用者確認的真實旋律不可由演算法信心取代。原 M1／工作譜／修訂保持不變。

```sh
docker compose run --rm --no-deps -v "$PWD/backend:/app" backend bash -c 'python -m pip install --cache-dir /app/output/evaluation/benchmark-pip-cache --no-deps --only-binary=:all: --target /tmp/essentia-benchmark essentia==2.1b6.dev1389 && PYTHONPATH=/tmp/essentia-benchmark:/app python -m app.evaluation.melodia_followup /app/output/work/jobs/12fac6df94ee48a282fe2c542df3ae22/accompaniment-stem.wav /app/output/evaluation/melodia-benchmark-2026-10-04/M1-accompaniment.json /app/output/evaluation/NEW_DIRECTORY'
```

套件仍只安裝在拋棄式容器；本機 output 僅快取下載套件，避免每輪重下載，未修改正式依賴。來源 JSON、參數、基準 hash、分段比較寫入獨立報告。23 項 adapter／來源／G／候選相關測試通過。

## 本輪結果與必要測試

- control 與原 M1 的完整上下文頻率陣列完全相同，基準重現通過。
- W 與 control 完整上下文頻率陣列完全相同；本段沒有得到支持音域上限問題的新證據，不要求使用者重聽等價檔。
- R 在前 7 秒增加 243 個有聲影格（約 0.705 秒），不刪除或修改原有有聲影格音高；新增位置為試聽檔約 2.984–3.233 秒及 3.361–3.817 秒。
- R 的 227–233 秒音高／休止影格與 M1 逐項完全相同，不是只通過半音容差。沒有手動拼接。連續合成的相位可能因前段新增音符而不同，不能稱整段 PCM 位元相同。
- 瀏覽器已確認 R 可解碼為 13 秒、有非零音訊。產物 `output/evaluation/melodia-followup-2026-10-04/`；原資料未動。
