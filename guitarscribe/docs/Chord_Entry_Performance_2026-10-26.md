# Codex：可選的和弦入口演奏預覽

日期：2026-10-26。工程完成；第三來源連續版初步可接受，跨來源音樂品質尚待確認。

## 已取得的判斷

使用者先回覆單次彈奏 B「好像變好了」，再回覆固定相同入口、恢復連續刷奏的版本「好像 OK 喔」。支持改善演奏安排後保留連續刷奏的方向；不等於逐和弦正確、晚拍完全消失或全產品達標。第三來源這一段停止重測。

## 實作與可還原界線

`app/services/chord_entry_performance.py` 提供 `sparse`／`continuous` 明確選擇，先編譯原版，再產生獨立 manifest。每個可處理和弦的第一刷移至其保存邊界，後續刷奏保持原位置；聲音 sustain_end 到保存的和弦終點，沿用既有音色的 release。沒有修改 SongScore 或拍格、沒有推斷新的和弦位置。

人工修改、短於當地一拍、缺少拍長、沒有既有首刷、合併的同和弦跨度及各弦無法在下一刷／和弦結束前彈完時，均保留原跨度並回傳原因。無法處理整份譜的重疊、重複 ID、非有限時間或非遞增拍格則拒絕。略過區域的原有共鳴也保留，所以混合預覽仍可能有局部問題，不宣稱全曲品質通過。

新增獨立端點：

```text
POST /scores/chord-entry-performance
{score: SongScore, mode: "sparse" | "continuous", output: "preview" | "midi"}
```

preview 回傳 original／candidate、變更、略過原因、revision，以及 `applied:false`／`saved:false`。還原就是選回 original；它不寫資料庫，也不把策略塞進原譜。MIDI 由同一 candidate manifest 匯出，回應帶 `X-Playback-Revision`。既有 `/scores/...` 播放／匯出預設未改，主 UI 尚未串接；不宣稱使用者已可在主工作區選這個方案。API 已經 ASGI 路由測試，本輪不為未使用的端點重啟既有本機分析服務。

連續模式的 MIDI note-off 設在下一刷或和弦終點，避免第一刷像診斷 manifest 一樣在 MIDI 中持續重疊。瀏覽器使用 sustain_end，與第三來源已聽版本的所有聲學參數逐項一致，僅事件 ID 與供 MIDI 使用的 end 正規化。MIDI 不重現瀏覽器合成器的共鳴及 280ms release，不能宣稱兩者音色／延音完全相同。MusicXML 記譜仍來自原譜，本輪不加入此演奏編排。

## 驗證結果

66 項相關測試通過（演奏預覽、時間候選、伴奏候選、MIDI）：涵蓋原版不變／可切回、不同模式、人工／短和弦／合併跨度保護、刷弦越界保護、壞資料拒絕、MIDI note-on/off 與 manifest 對照及 API 必填模式／相同 revision。

三個既有來源做結構回歸：

| 來源 | 處理跨度 | 保留原樣 | MIDI 最大時間誤差 |
| --- | ---: | ---: | ---: |
| 第三來源 | 10 | 0 | 1.00ms |
| 現場來源完整 45 秒 | 18 | 3 | 約 1.00ms |
| 小手拉大手既有裁切 | 6 | 1 | 0.88ms |

這些是工程數據，不是音樂準確率。回歸工具 `backend/scripts/check_entry_performance_regression.py` 保留原始資料並產生證據；版本化小型資料在 `docs/diagnostics/2026-10-26/entry-performance/`。不重跑分離或模型，不新增音源、不上傳。

## 唯一下一步

現場來源固定原曲 10–40 秒：A 重用先前較合拍的 B 原音檔，B 使用新 continuous 方案。相同來源、和弦、拍格及固定混音增益；A SHA 完全一致，沒有每版個別音量正規化。兩版同為 450 個弦音，渲染無截波、尾端歸零；頁面 HTTP 200、播放互斥、跳轉續播及載入均通過。

只請使用者各聽一次 30 秒，回答「B 較順／差不多／A 較順／兩個都不對／聽不清楚」。這一段的 A 曾被偏好，但不是逐和弦真值。如果新方案退步，保留原版並查具體演奏差異，不調整整首速度或擴大拍點吸附。即使通過，也只支持這兩個既有片段的演奏安排；旋律問題與全曲／更多來源驗證仍未完成。
