# 歌曲結構辨識、結構化練習與反覆沿用：故事與執行計畫

更新：2026-11-17。SS01／ST5／ST7 新歌工程缺口已補齊：介面啟動、進度恢復、取消、預覽、明確套用及大段練習；實際《可惜不是你》17段初稿已備妥。ST8–ST11 工程已實作、驗證及發布；ST3音樂品質仍待核對，不宣稱自動標註全曲正確。

## 1. 使用者決策與要解決的問題

使用者認為目前視覺化已能幫助判斷根音，但一百多個逐段填寫項目太累。希望像一般吉他譜，先看前奏、主歌、副歌、間奏、尾奏，再用反覆或重複關係減少工作。

**2026-11-15 已明確選擇：先做好主歌／副歌等名稱辨識，再做沿用。** 因此第一階段的交付是有音樂功能名稱的歌曲結構初稿、核對與修正；不以單純 A／B 相似分群取代這個目標。重複分群、複製根音和反覆譜式是後續階段。

本次「討論執行」先產出可審閱故事與工作切片；已開始唯讀可行性查核。現有視覺練習與保存稿繼續可用。後續開發遵循 TDD，先重現失敗情境，再實作與回歸。

## 2. 先釐清「完整正確拆解」

目標合理，但不能預先保證任意歌曲全自動、百分之百正確。產品應提供可完整覆蓋原曲、能核對與修正的結構，而不是強迫每個區間都有看似確定的名稱。

| 問題 | 例子 | 是否能推導下一層 |
| --- | --- | --- |
| 段落邊界在哪裡？ | 0:40 是否開始新段 | 邊界正確不代表名稱正確。 |
| 段落的音樂功能是什麼？ | 主歌、預副歌、副歌、橋段 | 同名不代表使用相同根音或和弦。 |
| 哪些段落互相重複或變奏？ | 主歌 1 與主歌 2 | 相似不代表每小節一致，也可能只有部分重複。 |
| 哪些判斷可以沿用？ | 副歌 2 沿用副歌 1，但末兩小節不同 | 需要時間／拍位對齊與差異核對。 |

第一階段能減少「一次面對所有小段」的負擔；真正減少相同根音的重複輸入，須完成後續沿用功能。不能只把畫面折收，就宣稱辨識工作量已減少。

不要強制每首都有五種段落：可能直接從副歌開始、沒有前奏、沒有間奏、尾奏漸弱，或整曲沒有清楚的主副歌對比。橋段不等於間奏；沒有主唱也不必然是間奏。兩個名稱合理的模糊處，允許保留候選和備註。

結構層與低頻根音層使用不同證據。低頻圖仍用來練根音；主副歌辨識需考慮全頻音訊及較長的上下文，不能只挑低頻最亮線、最大音量或固定第幾小節命名。

## 4. 預期使用流程

下例只示意操作，不是目前任何歌曲的實際分析。

```text
載入原曲 → 分析歌曲結構 → 看全曲順序 → 回聽／修正 → 保存結構

前奏 → 主歌 1 → 副歌 1 → 間奏 → 主歌 2 → 副歌 2 → 尾奏
                     ↓ 點選副歌 1
        顯示這段的頻譜、原曲回聽及根音練習區段

第二階段：選副歌 2 → 比較副歌 1 → 預覽可沿用處 → 只修不同處
第三階段：結構譜顯示演奏順序、重複段與不同結尾；仍能展開整首
```

主要畫面以「歌曲段落」導覽；目前段落內才顯示細部「練習區段」。有可靠拍格才顯示小節編號，否則顯示秒數。名稱加上 1／2 只表示出現次序，不表示相同內容。

## 7. 第一階段的技術方案

### 7.1 先試真正的功能名稱模型

首選評估原作者的 [All-In-One Music Structure Analyzer](https://github.com/mir-aidj/all-in-one)。它提供功能段落邊界與名稱預測；我們只評估結構輸出，不用其 BPM／重拍覆寫既有拍格。官方列出的 Linux 安裝涉及 NATTEN、madmom；本機需隔離測試相容性，不能直接升降正式 runtime。

其[標籤定義](https://github.com/mir-aidj/all-in-one/blob/main/src/allin1/config.py)包含 intro、outro、verse、chorus、bridge、inst、solo、break、start、end。產品映射規則：

| 原標籤 | 初稿顯示 | 限制 |
| --- | --- | --- |
| intro／outro | 前奏／尾奏（待確認） | 不以出現在最前／最後就強行命名。 |
| verse／chorus | 主歌／副歌（待確認） | 次序編號不是內容相同的證明。 |
| bridge | 橋段（待確認） | 不直接翻成間奏。 |
| inst／solo | 器樂段／獨奏段（間奏候選） | 結合前後段落供回聽確認，不將無主唱一律視為間奏。 |
| break | 停頓／過渡段（待確認） | 依上下文修正，不硬併入副歌。 |
| start／end | 原模型邊緣標記，保留原值；介面暫列未判定 | 不等同前奏／尾奏，也不自行認定為靜音。 |
| 模型無對應類別 | 人工可選預副歌、自訂名稱或未判定 | 不宣稱模型已自動辨識它不支援的類別。 |

優先固定原作者版本與模型權重。若原版安裝／執行不相容，記錄問題，再比較可追溯的推論移植；不能悄悄更換引擎或只因可安裝就聲稱等價。程式庫 MIT 授權已查，權重與必要相依套件的來源／條件仍需在引入前逐項核實。

本輪尚未測試模型在中文歌曲的效果。發現可用預訓練模型，只能證明有具體實作起點，不能證明這兩首已能完整正確拆解。

### 7.2 相似度方法放在適合的位置

librosa 的自相似／分段方法可作邊界與重複關係的比較證據，但不能直接把 A 群叫主歌、B 群叫副歌。因此它不是第一階段語義名稱辨識的替代品，主要留給差異診斷與第二階段。

沿用原曲、合適且來源吻合的分軌快取；缺少模型所需特徵才另外計算。既有根音分數可供對照，不當結構答案。沒有歌詞也要能分析；已有正確定位歌詞可作輔助，不要求使用者先補整首歌詞。

### 7.3 核對介面不能製造另一百個填寫欄

第一版提供一條可點選的全曲結構帶與一份簡短段落清單。點段落即可聽原曲；主要動作是「名稱正確」「改名稱」「調整起訖」，不是填每個小節的結構表單。

模型候選保持待確認。可依歌曲逐段確認，不要求一次核對整首才能練習。分析失敗時仍可手動圈歌曲段落；但手動入口不能取代自動名稱辨識的驗收。

確認狀態分別追蹤名稱與邊界。移動兩段共用的邊界，兩側的邊界確認都失效；分開／合併後的新段需重新核對，不直接繼承「已確認」。保留原模型名稱與人工修正名稱，方便知道改了什麼；未受影響的段落保持原狀。

## 8. 資料與相容性約定

新增獨立的結構文件與版本契約，避免把欄位硬塞進目前禁止額外欄位的 RootDocument v1／v2。第一階段修改結構只寫結構資料。

| 資料 | 必須保存的意義 |
| --- | --- |
| 來源 | job、原音訊 hash、片段範圍、duration；另外保留與現有根音稿 fingerprint 的關聯。 |
| 結構版本 | 初稿／修改稿版本、引擎與權重版本、參數、輸入 hash、耗時與失敗狀態。 |
| 每次出現 | 穩定 occurrence ID、來源局部起訖、模型原標籤、顯示名稱、候選／確認狀態。 |
| 對齊資訊 | 拍格版本與局部拍位映射；無可靠拍格時保留秒數，不假造小節號。 |
| 後續重複關係 | 關係類型、代表段／目標段、對齊版本、局部例外、是否已核對。 |

現有 root fingerprint 包含原分析和弦與 provenance，不是純音訊 hash。原分析更新或換錄音時，分別檢查音訊是否相同、時間範圍是否相同與映射是否過期；不可只因歌曲名稱相同就沿用。

改拍格、重切練習段會改 ID；長期結構關聯不能只綁根音 segment ID。結構邊界先留來源秒數，映射過期則提示待重新核對，不自動搬動已確認內容。

結構可與根音小段邊界不同。導覽可顯示交疊小段並標出原起訖，但不能為了結構折收偷偷截短或重切原根音；根音採用仍明示實際寫入範圍。

結構保存需有版本衝突保護、離線草稿與備份。原「下載完整練習」目前只含根音文件；新介面須清楚區分舊根音備份與包含結構的新完整備份，並保留舊檔匯入能力。

## 9. 後續沿用與反覆的行為約定

這些是第二／三階段規劃，第一階段不實作：

- 同名只提供比較入口，不自動建立「可共用根音」關係。只有根音已核對時，僅能沿用根音，不順帶宣稱完整和弦、最低音、轉位或節奏相同。
- 第一次先支援等拍數、對應清楚、分段相容的段落；速度不同不能只加固定秒數偏移。弱起、加減小節、轉調或無可靠拍格先標出待處理，不強拉對齊。
- 沿用建議放在獨立預覽。現有 schema 中 root 非空即 confirmed，不能把機器建議直接寫成「已採用」。
- 明確接受後才以單次版本化操作填入未採用目標；已採用衝突逐項保留，來源未判斷處不擴散。過期預覽、跨版本或部分儲存失敗不得留下半套更新。
- 各次出現可獨立修改。代表段後續變更只提示可重新比較，不自動覆寫別次；沿用前的人工工作可復原。
- 錄音時間線保留每一次實際出現。緊鄰且確認相同的部分才可顯示「反覆 ×2」；主歌和間奏隔開的兩次副歌應用段落參照／順序表示。
- 不同結尾、延長與轉調有明確註記；不靠刪除例外使譜面變短。完整傳統 D.S.／D.C.／Coda 跳躍與 MusicXML 反覆匯出，待基本順序與變奏已可驗證後再排入。

## 10. 排序代辦與 TDD

`ready` 指可以成為下一個工作切片；不是已實作。每項依「新增失敗測試 → 最小實作 → 相關回歸 → 整理」執行。模型音樂正確性需獨立參考，單元測試不能證明。

| 順序 | 任務 | 依賴／狀態 | 先重現或固定的驗收情境 |
| --- | --- | --- | --- |
| ST0 | 釐清名稱優先、查核現有來源／依賴、故事與地圖、跨 session 分工 | done（本文件） | 確認現有159／151區段意義；不能把名稱分群當和聲相同。 |
| ST1 | 固定結構類別、參考標註規則、首輪曲目、候選版本與退回條件 | done | 開曲就是副歌、沒有前奏、間奏與橋段不同、無法確定的名稱；先定規則再看模型結果。 |
| ST2 | 隔離環境執行語義結構模型，產出來源可追溯的離線結果 | done（兩曲） | 輸入錯誤、缺權重、執行失敗／取消、來源 hash 不符；失敗不影響現有分析。 |
| ST3 | 做名稱／邊界比較與可回聽報告，決定是否採用候選 | 回聽／評分工程 done；品質 awaiting_human | 整首有覆蓋不等於全對；逐曲報錯標、漏段、過切、邊界及未知區域。 |

## 11. 驗證與停止條件

### 音樂品質

- 先固定《膽小鬼》《沒那麼簡單》的實際錄音／hash／片段，再從已有合法來源選一首未用來調參的保留曲；第三首尚未指定，不算已具備三曲驗證。
- 參考標註獨立於模型候選，記錄標註者、證據、模糊邊界與可接受名稱；另一模型或同名網路譜不是本錄音真值。尚無參考時只報運算與結構合理性，不報正確率。
- 邊界分別報固定 0.5 秒與 3 秒容差的 precision／recall／F1；名稱另外報按時長計的標籤結果、各類混淆及未判定覆蓋。兩者不可混成一個「完整正確率」。
- 第一階段逐曲列出需改名、移界、加段／刪段的數量與所需操作；評估是否比從空白標整首省事。尚未實測，先不承諾固定節省百分比。
- ST1 必須在看候選結果前另存固定評估協定，寫清各類最低有效標註量、可接受的主副歌錯標／漏段上限、整曲修正量與本機資源上限；ST3 不可看完結果再放寬。若缺獨立參考，只能交付運行與待核對結果，不能宣布通過名稱品質門檻或升為正式預設。
- 若模型把多個主要主歌／副歌混淆、需大量重切或無法在本機穩定執行，記錄失敗並保留現有版本，不把錯誤初稿升成預設。更換方法需提出新的可驗證假設，不逐曲硬寫段落時間。
- 第二階段再量化少掉多少重複輸入，扣除關係建立、核對與修錯成本；不能以刪掉待聽段或增加誤採用換取省步數。

### 工程與資料

- 模擬測試包含：相同段重複、同名但不同根音、不同尾句、弱起、無前奏、變速、轉調、零／缺失來源、來源偏移只加一次。
- 第一階段結構編輯前後，根音稿與原分析完全相同；正式使用者歌曲只讀驗證，會寫入的測試使用隔離資料。
- 延續現有 45 項根音測試中受影響的必要回歸，新增結構 API／播放器／保存測試；最終再跑完整相關回歸、build 及兩曲正式入口查核。
- 以與主流程相同的音訊時鐘測跳段、回聽及跨邊界；不啟用模型的 sonification 來替代原曲播放。
- 本次規劃不改手機連線、不啟動新旋律辨識、不上傳錄音到外部服務、不購買分析服務。

### 2026-11-17 使用者再次指出的必要驗收
