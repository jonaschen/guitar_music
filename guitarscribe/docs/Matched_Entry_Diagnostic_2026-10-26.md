**後續回饋：使用者「好像 OK 喔」。** 記為本片段連續演奏初步可接受；沒有完整品質評分，不能宣稱旋律、全部和弦或其他來源已通過。此段不再重聽。已整理獨立演奏預覽與 MIDI 一致性檢查，下一步為其他既有來源回歸，見 [整合紀錄](Chord_Entry_Performance_2026-10-26.md)。

## 回饋與假說

使用者對 boundary-only B 回覆「B 好像變好了」。這是初步偏好，不是品質達標、和弦正確、晚拍消失或跨來源驗收。前一組同時改變首刷等待、刷奏密度及累積共鳴；這輪固定改善版的入口，只恢復中間刷奏。

## 固定條件與唯一變項

使用第三來源原曲 20–40 秒；不跑辨識、不改譜、不改拍格或和弦邊界。

- A：上一輪 B 的原始音檔與 manifest（10 次彈奏），發布 SHA 完全一致。
- B：完整保留 A 的所有事件，再加入原連續刷奏中每個和弦第一刷以後的 44 次事件。所有新加事件在原保存位置發聲，音高、力度、弦偏移與方向均保留；sustain_end 統一為其保存和弦終點。
- 兩版相同入口、相同音色／280ms release 設定、相同 source crop、相同固定混音增益。此輪只有新增刷奏及其自然產生的累積共鳴，沒有額外調淡或縮短尾音。

新 B 與曾被拒絕的連續刷奏不同：第一下不再等待後面的刷奏格，上一和弦也不延續到後面的首刷時刻。這是獨立診斷 manifest，不是已整合的通用策略；合法離拍與細碎轉換仍需另外保護。

## 工程檢查與投入

使用既有資料做一組 20 秒 A/B，沒有新增模型或外部操作。檢查十個共同入口與原有事件逐欄一致、44 個新增事件位於各自和弦內、唯一 event ID、來源／控制音檔雜湊、固定音量、排程與實際渲染一致、無截波、尾端歸零。瀏覽器驗證 HTTP 200、兩段各 20.35 秒（含尾音）、播放互斥、跳轉續播與無頁面錯誤。

重現：執行 `backend/scripts/prepare_matched_entry_review.py`，再於 frontend 執行：

```sh
node scripts/render-chord-attack-diagnostic.mjs ../output/evaluation/matched-entry-2026-10-26 matched-entry-2026-10-26 scripts/matched-entry.html
```

需要本機既有音訊；輸出目錄須不存在。小型證據存於 `docs/diagnostics/2026-10-26/matched-entry/`，音訊留本機。主 UI、工作譜、正式 compiler 及分析預設均不改。

## 唯一下一步與停止條件

請使用者各聽一次，回答「B 仍自然／A 較自然，B 又變亂／兩個都不對／差異聽不清楚」。若 B 保留改善，才有依據繼續研究保留連續刷奏的入口安排；若 A 仍較好，保留稀疏版基準並檢查密度／共鳴。此結果不單獨證明哪一個原機制是根因；不反覆要求同版驗收、不直接全域吸附或改預設。
